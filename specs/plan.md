# RemoteConnect — план реализации

**Статус:** утверждён; этапы 0–6 реализованы в объёме MVP (v0.1), см. §8
**Дата:** 2026-10-23
**Основание:** [spec.md](spec.md) v0.2

---

## 1. Технические решения

| Область | Решение | Почему |
|---|---|---|
| Платформа | .NET 10, WPF, x64 | NFR-1, NFR-2 |
| MVVM | CommunityToolkit.Mvvm | Источник-генераторы для свойств и команд, минимум шаблонного кода |
| Транспорт | `TcpListener`/`TcpClient` + `SslStream`, TLS 1.3 | Встроено в .NET, FR-SEC-1 |
| Сертификат хоста | Самоподписанный ECDSA P-256 через `CertificateRequest`, хранится в PFX, ключ защищён DPAPI | FR-SEC-1, без внешних зависимостей |
| Проверка пароля | Challenge-response: `HMAC-SHA256(PBKDF2(пароль, соль), nonce ‖ отпечаток сертификата хоста)` | Пароль не передаётся (FR-SEC-2); привязка к сертификату мешает переиспользовать ответ через подменённый хост |
| Хранение пароля | Хранится только PBKDF2-ключ (600 000 итераций, SHA-256), зашифрованный DPAPI | FR-SEC-3 |
| UPnP | Библиотека Mono.Nat (UPnP IGD + NAT-PMP) | Поддерживается, умеет оба протокола |
| Внешний IP | HTTPS-запрос к api.ipify.org, запасной — icanhazip.com | FR-NET-3 |
| Захват экрана | Desktop Duplication API через Vortice.Direct3D11/DXGI; запасной путь — GDI `BitBlt` | DXGI отдаёт список изменённых областей (dirty rects) — основа FR-SCR-2 и NFR-6 |
| Сжатие | Разбиение кадра на плитки 64×64, отправка изменённых плиток в JPEG через libjpeg-turbo (обёртка TurboJpegWrapper); запасной кодек — WIC | Быстрее WPF-кодеков в разы, NFR-5/NFR-6 |
| Отображение | `WriteableBitmap`, плитки декодируются в фоне и копируются в буфер | Без лишних аллокаций, без перерисовки всего кадра |
| Ввод | `SendInput` через P/Invoke (Microsoft.Windows.CsWin32) | FR-INP-1/2 |
| Перехват Alt+Tab/Win | Low-level keyboard hook на управляющей стороне, активен только пока окно просмотра в фокусе | FR-INP-4 |
| Брандмауэр | `netsh advfirewall` в отдельном процессе с повышением прав (по кнопке) | FR-NET-7, обычная работа без прав администратора (NFR-3) |
| Настройки | JSON в `%APPDATA%\RemoteConnect\settings.json` | Просто, читаемо |
| Логи | Serilog, файловый приёмник в `%LOCALAPPDATA%\RemoteConnect\logs` | NFR-8 |
| Тесты | xUnit | Стандарт для .NET |
| Поставка | `dotnet publish` self-contained single-file, PerMonitorV2 DPI в манифесте | NFR-3, NFR-9 |

Версии пакетов фиксируются на этапе 0 по последним стабильным релизам.

## 2. Структура решения

```
RemoteConnect.sln
src/
  RemoteConnect.Core/              — без зависимостей от WPF и Win32
    Protocol/                      — сообщения, сериализация, кадрирование
    Security/                      — PasswordVerifier, AuthRateLimiter, OneTimePassword
    Session/                       — машины состояний хоста и клиента, SessionController
    Imaging/                       — TileDiffer, модель плиток, пересчёт координат
  RemoteConnect.Windows/           — всё, что зависит от Windows API
    Capture/                       — DxgiCapturer, GdiCapturer, CursorTracker
    Encoding/                      — JpegTileEncoder (turbo / WIC)
    Input/                         — InputInjector (SendInput), KeyboardHook
    Network/                       — UpnpPortMapper, PublicIpResolver, NatDiagnostics, FirewallHelper
    Security/                      — CertificateStore, DpapiProtector
  RemoteConnect.App/               — WPF
    Views/                         — MainWindow (вкладки), ViewerWindow, ConsentWindow, SessionBar
    ViewModels/
    Services/                      — SettingsService, HostService, ConnectService
tests/
  RemoteConnect.Core.Tests/
  RemoteConnect.Windows.Tests/     — интеграционные: TLS-сессия по loopback, захват/кодирование
specs/
```

Правило зависимостей: `App → Windows → Core`. Core тестируется без Windows-окружения.

## 3. Протокол

### 3.1 Кадрирование
Поверх TLS-потока: `[тип: 1 байт][длина: 4 байта, LE][полезная нагрузка]`. Максимальный размер сообщения — 16 МБ. Сериализация — ручная через `BinaryWriter`/`BinaryReader` (без рефлексии, предсказуемо по скорости).

### 3.2 Сообщения

| Тип | Направление | Содержимое |
|---|---|---|
| `Hello` | клиент → хост | версия протокола, имя пользователя, запрошенная роль клиента (`Controller` / `Controlled`) |
| `AuthChallenge` | хост → клиент | соль, число итераций, nonce (32 байта) |
| `AuthResponse` | клиент → хост | HMAC (32 байта) |
| `AuthResult` | хост → клиент | `Ok` / `WrongPassword(attemptsLeft)` / `Blocked(secondsLeft)` / `Busy` / `VersionMismatch` |
| `ConsentRequest` | к управляемой стороне | имя управляющего, отпечаток сертификата |
| `ConsentResult` | от управляемой стороны | `Allowed` / `Denied` / `TimedOut` |
| `ScreenInfo` | управляемая → управляющая | список мониторов, активный монитор, размер, DPI |
| `FrameTiles` | управляемая → управляющая | номер кадра, набор плиток `(x, y, w, h, jpeg)` |
| `FrameAck` | управляющая → управляемая | номер кадра |
| `CursorPos` / `CursorShape` | управляемая → управляющая | позиция; форма курсора (PNG + hotspot), только при смене |
| `MouseInput` | управляющая → управляемая | нормализованные координаты 0..65535, кнопки, колесо |
| `KeyInput` | управляющая → управляемая | виртуальный код, скан-код, флаги (down/up, extended) |
| `ReleaseAll` | управляющая → управляемая | отпустить все зажатые клавиши/кнопки |
| `SelectMonitor` | управляющая → управляемая | индекс монитора |
| `InputEnabled` | управляемая → управляющая | разрешён ли ввод (FR-SEC-8) |
| `Ping` / `Pong` | обе | отметка времени |
| `Bye` | обе | причина |

### 3.3 Порядок установления сессии
```
TCP connect → TLS (клиент сверяет сертификат с сохранённым, TOFU)
→ Hello → [проверка: занят? заблокирован? версия?]
→ AuthChallenge → AuthResponse → AuthResult
→ ConsentRequest на управляемой стороне → окно «Разрешить?» (60 с)
→ ConsentResult(Allowed) → показ плашки на управляемой стороне
→ ScreenInfo → поток FrameTiles / ввод
```
Хост проверяет блокировку IP **до** выдачи challenge. До `ConsentResult(Allowed)` управляемая сторона не захватывает экран и игнорирует любые `MouseInput`/`KeyInput` — это проверяется в машине состояний, а не в UI.

### 3.4 Управление потоком кадров
Управляемая сторона держит не более 2 неподтверждённых кадров (`FrameAck`). Если канал медленный — кадры пропускаются, накопленные изменения сливаются в следующий. Так задержка не растёт при узком канале, а при статичном экране трафик нулевой (NFR-4, NFR-5).

### 3.5 Обрыв соединения
`Ping` каждые 2 с; нет ответа 6 с — соединение считается потерянным (NFR-7). При потере связи управляемая сторона сразу вызывает `ReleaseAll` локально, прекращает захват и убирает плашку.

## 4. Ключевые компоненты

| Компонент | Ответственность | Требования |
|---|---|---|
| `HostService` | Запуск/остановка ожидания, UPnP, таймер авто-остановки, приём единственной сессии | FR-NET-1, 2, 10, 11 |
| `NatDiagnostics` | Внешний IP через UPnP и через HTTPS, определение CGNAT, проверка hairpin | FR-NET-3, 4, 8 |
| `AuthRateLimiter` | Счётчик ошибок по IP, блокировки с истечением, ручная разблокировка, событие для UI | FR-SEC-4, 9 |
| `PasswordVerifier` | Генерация challenge, проверка ответа (сравнение за постоянное время) | FR-SEC-2, 3 |
| `OneTimePassword` | Генерация пароля `xxx-xxx` из алфавита без похожих символов (без 0/O, 1/l/I) криптостойким ГСЧ | FR-SEC-10 |
| `SessionController` | Машина состояний: `Handshake → Auth → AwaitingConsent → Active → Closed`; маршрутизация сообщений по роли | FR-SEC-5, NFR-7 |
| `ScreenStreamer` | Цикл захват → дифф плиток → кодирование → отправка с учётом `FrameAck` | FR-SCR-1, 2, 3, 5 |
| `ViewerWindow` | Отрисовка, масштабирование, полноэкранный режим, сбор ввода, пересчёт координат | FR-SCR-4, FR-INP-1..4 |
| `InputInjector` | Применение ввода через `SendInput`, учёт зажатых клавиш для `ReleaseAll` | FR-INP-1..3 |
| `ConsentWindow` | Окно подтверждения поверх всех окон, авто-отказ через 60 с | FR-SEC-5 |
| `SessionBar` | Плашка поверх всех окон: кто управляет, «Только просмотр», «Отключить»; не закрывается, пока идёт сессия | FR-SEC-6, 8 |

## 5. Этапы

Каждый этап заканчивается работающей сборкой, зелёными тестами и демонстрацией. После каждого этапа — короткий отчёт и ваше «ок» перед следующим.

### Этап 0. Каркас
- Решение и проекты по структуре из раздела 2, ссылки на пакеты, `Directory.Build.props` (nullable, предупреждения как ошибки).
- `SettingsService`, логирование, пустое главное окно с вкладками «Хост» / «Подключиться».
- `git init`, `.gitignore`.

**Готово, когда:** `dotnet build` и `dotnet test` проходят, приложение запускается и показывает две пустые вкладки.

### Этап 1. Протокол, TLS и авторизация
- Кадрирование и сериализация всех сообщений.
- Сертификат хоста, TLS-рукопожатие, TOFU на клиенте.
- `PasswordVerifier`, `OneTimePassword`, `AuthRateLimiter`, хранение пароля через DPAPI.
- `SessionController` до состояния `AwaitingConsent` (согласие пока автоматическое — только в тестах).

**Требования:** FR-NET-1, 9, 10; FR-SEC-1..4, 10.
**Тесты:** сериализация туда-обратно для каждого сообщения; верный/неверный пароль; 5 ошибок → `Blocked`; истечение блокировки; ручная разблокировка; `Busy` для второго клиента; полная сессия по loopback с TLS.

### Этап 2. Сеть хоста
- `UpnpPortMapper`: открытие порта при старте, закрытие при остановке и выходе (включая аварийное — через обработчик завершения процесса).
- `NatDiagnostics`: внешний IP, CGNAT, hairpin-проверка.
- Таймер авто-остановки.
- `FirewallHelper` по кнопке.

**Требования:** FR-NET-2..8, 11.
**Тесты:** логика определения CGNAT на наборах адресов; таймер авто-остановки (с подменяемыми часами). UPnP проверяется вручную на вашем роутере.

### Этап 3. Интерфейс подключения и согласия
- Вкладка «Хост»: старт/стоп, статус с причиной ошибки, строка подключения + пароль + «Скопировать», режим пароля, таймер авто-остановки, список блокировок с «Разблокировать», локальные IP.
- Вкладка «Подключиться»: адрес, пароль, выбор режима («Управлять удалённым ПК» / «Разрешить управление моим ПК»), история адресов, сообщения об ошибках из `AuthResult`.
- `ConsentWindow`, `SessionBar`, отпечаток сертификата на обеих сторонах.

**Требования:** FR-UI-1..4, FR-SEC-5..9, FR-NET-5, 6.
**Готово, когда:** два экземпляра на одном ПК проходят С1–С4 вплоть до пустого окна просмотра; отказ в согласии и таймаут 60 с корректно завершают сессию у обеих сторон.

### Этап 4. Трансляция экрана
- `DxgiCapturer` + `GdiCapturer` (автоматический переход при ошибке DXGI, например в RDP-сессии).
- `TileDiffer`, `JpegTileEncoder`, `ScreenStreamer` с управлением потоком.
- Курсор: позиция и форма.
- `ViewerWindow`: отрисовка, масштабирование, полноэкранный режим.

**Требования:** FR-SCR-1..4, NFR-5, NFR-6, NFR-9.
**Тесты:** дифф плиток на синтетических кадрах; бенчмарк кодирования 1920×1080; замер FPS, трафика и CPU в локальной сети.

### Этап 5. Ввод
- Сбор мыши и клавиатуры в `ViewerWindow`, пересчёт координат с учётом масштаба, отступов и DPI.
- `InputInjector`, `ReleaseAll` при потере фокуса и при обрыве.
- Keyboard hook для Alt+Tab / Win.
- «Только просмотр» на плашке.

**Требования:** FR-INP-1..4, FR-SEC-8, NFR-4, NFR-7.
**Тесты:** пересчёт координат (масштаб, letterbox, DPI); учёт зажатых клавиш. Вручную — критерий приёмки 6.

### Этап 6. Доводка и приёмка
- Переключение мониторов (FR-SCR-5).
- «Перезапустить от администратора» на управляемой стороне.
- Публикация single-file exe.
- Прогон всех критериев приёмки из spec.md §9 между двумя ПК в разных сетях; отчёт по каждому пункту.

## 6. Риски

| Риск | Последствие | Что делаем |
|---|---|---|
| DXGI недоступен (RDP-сессия, некоторые гибридные видеокарты, смена разрешения) | Нет картинки | Автоматический переход на GDI; переинициализация при `DXGI_ERROR_ACCESS_LOST` |
| Роутер без UPnP или UPnP выключен | Хост недоступен извне | Понятное сообщение с инструкцией по ручному пробросу (С5) |
| Серый IP у хоста | Подключение невозможно | Диагностика CGNAT; совет поменяться ролями хоста или использовать Tailscale |
| Роутер не поддерживает hairpin NAT | Проверка доступности ложно-отрицательная | Показываем «не удалось проверить», а не «недоступен» (В1) |
| UIPI: окна администратора не принимают ввод | Часть окон не управляется | Кнопка «Перезапустить от администратора» на управляемой стороне (этап 6) |
| Производительность JPEG ниже NFR-5 | Низкий FPS | Замер на этапе 4; при необходимости — снижение качества, затем H.264 через Media Foundation (В4, v2) |

## 7. Не входит в этот план
Всё из spec.md §3.2: передача файлов, буфер обмена, звук, relay-сервер, неконтролируемый доступ, защищённый рабочий стол.

## 8. Статус реализации (v0.1)

Реализованы все требования приоритета M и большинство S. Проверено: 78 автотестов (юнит + интеграционные:
TLS-сессия по loopback, блокировки, захват и JPEG, реальный ввод через SendInput) и ручной прогон
сценариев С1–С5 двумя экземплярами на одном ПК.

### Отклонения от плана

| Пункт плана | Как сделано | Почему |
|---|---|---|
| Захват через Desktop Duplication (DXGI) | GDI `BitBlt` + собственный поиск изменений по плиткам | Проще и надёжнее для MVP (работает и в RDP); на тестовом ПК даёт ~16 кадров/с. DXGI — следующая оптимизация |
| JPEG через TurboJpegWrapper | SkiaSharp 3.x (внутри libjpeg-turbo) | Один поддерживаемый пакет с нативными библиотеками для single-file |
| TLS 1.3 | TLS 1.2 или 1.3 — по возможностям ОС | SChannel в Windows 10 не поддерживает TLS 1.3 на стороне сервера |
| Сообщения `ConsentRequest`, `CursorPos`/`CursorShape` | Не нужны: управляемая сторона знает свою роль из handshake; курсор рисуется прямо в кадр | Меньше сообщений, проще протокол |
| Microsoft.Windows.CsWin32 | Ручные P/Invoke в `RemoteConnect.Windows/Interop` | Нужен небольшой набор функций |

### Не сделано / следующие шаги

- FR-SCR-6 (C): адаптация качества под канал — сейчас фиксированное качество JPEG 70 и не более 20 кадров/с; задержка ограничена контролем потока (≤ 2 кадра в пути).
- FR-UI-5 (C): иконка в трее.
- FR-SEC-7 (S): отпечаток показан на обеих сторонах, TOFU-проверка работает; голосовая сверка — на усмотрение пользователей.
- Замеры NFR-4..NFR-6 на двух реальных ПК в разных сетях — во время первого теста с другом.
