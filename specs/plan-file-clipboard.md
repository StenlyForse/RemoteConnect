# RemoteConnect — план: файлы через буфер обмена

**Статус:** утверждён, в работе
**Дата:** 2026-10-23
**Основание:** [spec-file-clipboard.md](spec-file-clipboard.md) v0.2 (утверждена)
**Целевая версия:** v0.3.0, протокол версии 3

---

## 1. Как это работает — общая схема

```
ИСТОЧНИК (где Ctrl+C)                                 ПОЛУЧАТЕЛЬ (где Ctrl+V)
─────────────────────                                 ───────────────────────
Проводник кладёт в буфер список путей (CF_HDROP)
ClipboardSync видит изменение
FileOfferBuilder обходит файлы/папки в фоне,
проверяет лимиты 500 МБ / 10 000 / 5 с
  ── FileOffer(offerId, [путь, размер, папка?, дата]) ──►
                                                      FileNameValidator проверяет пути
                                                      VirtualFileDataObject → в буфер (OleSetClipboard)
                                                      … пользователь нажимает Ctrl+V в Проводнике …
                                                      Проводник читает список и для каждого файла
                                                      просит поток (FILECONTENTS, lindex)
                                                      RemoteFileStream.Read() — первый вызов:
  ◄── FileOpen(requestId, offerId, index) ──────────
FileTransferSource проверяет offerId и index,
открывает файл, сверяет размер
  ── FileChunk(requestId, 64 КБ) × окно 1 МБ ──────►  данные попадают в буфер потока,
  ◄── FileAck(requestId, байт) ─────────────────────  Проводник их читает и пишет на диск
  ── FileEnd(requestId) ───────────────────────────►
                                                      «Отмена» в Проводнике → поток освобождается:
  ◄── FileCancel(requestId) ────────────────────────
```

## 2. Технические решения

| Область | Решение | Почему |
|---|---|---|
| Виртуальные файлы | Свой COM-объект `VirtualFileDataObject`, реализующий `IDataObject` (System.Runtime.InteropServices.ComTypes) и `IDataObjectAsyncCapability`. Форматы: `FileGroupDescriptorW` (HGLOBAL), `FileContents` (IStream по `lindex`), `Preferred DropEffect` = копирование | Единственный способ «как в AnyDesk» (FR-FCB-6); готового в .NET нет |
| Асинхронная вставка | `IDataObjectAsyncCapability`: `GetAsyncMode` → true; Проводник выполняет копирование в фоне со своим окном прогресса | FR-FCB-8 — Проводник не зависает |
| Потоки | Управляемые COM-объекты .NET по умолчанию «agile» (free-threaded marshaler), поэтому вызовы Проводника из другого процесса приходят на потоки RPC, а не на UI-поток приложения. Блокирующее ожидание данных в `Read` допустимо | Иначе ожидание сети заморозило бы окно просмотра. **Проверяется первым делом на этапе 4** |
| Помещение в буфер | `OleSetClipboard` на UI-потоке. `OleFlushClipboard` **не** вызывается (он заставил бы отдать содержимое сразу). При конце сессии — `OleSetClipboard(null)`, если буфер всё ещё наш (`OleIsCurrentClipboard`) | FR-FCB-5, FR-FCB-18 |
| Передача | Потоковая, по запросу: `FileOpen` → `FileChunk` по 64 КБ с окном 1 МБ и подтверждениями `FileAck` | FR-FCB-7, NFR-FCB-2 (память на передачу ≤ окна) |
| Справедливость с экраном | В `Connection` две очереди отправки: обычная и «фоновая». Цикл отправки всегда сначала опустошает обычную; из фоновой берёт по одному сообщению. Кадр экрана ждёт не дольше одного чанка 64 КБ | FR-FCB-15 |
| Чтение на источнике | `FileStream` с `FileShare.ReadWrite \| Delete`, асинхронно; размер сверяется при открытии и в конце | FR-FCB-12, FR-FCB-13 |
| Таймауты | Ожидание данных в `Read` — до 15 с, затем ошибка `E_FAIL`; при закрытии соединения — немедленная ошибка | FR-FCB-14 |
| Безопасность | Источник отдаёт только `entries[index]` текущего `offerId` (никаких путей в запросе). Получатель проверяет имена до помещения в буфер | FR-FCB-16, FR-FCB-17 |

## 3. Протокол v3

`Handshake.ProtocolVersion = 3`. Новые сообщения:

| Тип | Направление | Содержимое |
|---|---|---|
| `FileOffer` | источник → получатель | `offerId`, список: относительный путь, папка?, размер, дата изменения (UTC ticks) |
| `FileOpen` | получатель → источник | `requestId`, `offerId`, `index` |
| `FileChunk` | источник → получатель | `requestId`, данные (≤ 64 КБ) — **фоновая очередь** |
| `FileAck` | получатель → источник | `requestId`, сколько байт прочитано Проводником |
| `FileEnd` | источник → получатель | `requestId` |
| `FileError` | источник → получатель | `requestId`, код: `OfferExpired`, `NotFound`, `AccessDenied`, `Changed`, `ReadError` |
| `FileCancel` | получатель → источник | `requestId` |

Новый `FileOffer` заменяет предыдущий; запросы к старому `offerId` получают `OfferExpired`.

## 4. Компоненты

| Компонент | Проект | Ответственность | Требования |
|---|---|---|---|
| `FileOfferBuilder` | Core | Обход выбранных файлов и папок (включая пустые), относительные пути от родительской папки, лимиты 500 МБ / 10 000 элементов / 5 с | FR-FCB-2, 3, 4 |
| `FileNameValidator` | Core | Проверка путей с другого ПК: без абсолютных путей, `..`, `:`, `<>"\|?*`, управляющих символов, зарезервированных имён (`CON`, `PRN`, `AUX`, `NUL`, `COM1-9`, `LPT1-9`), длина компонента ≤ 255 | FR-FCB-17 |
| `FileTransferSource` | Core | Текущий набор, обработка `FileOpen`/`FileAck`/`FileCancel`, окно отправки, проверка размера, коды ошибок, события прогресса | FR-FCB-5, 11–13, 16, 19 |
| `RemoteFileStream` | Core | Буфер принятых чанков для одного файла; блокирующее чтение с таймаутом; `FileAck` по мере чтения; `FileCancel` при закрытии раньше конца | FR-FCB-7, 11, 14 |
| `Connection` (доработка) | Core | Фоновая очередь отправки | FR-FCB-15 |
| `VirtualFileDataObject` | Windows | COM `IDataObject` + `IDataObjectAsyncCapability`; `FILEGROUPDESCRIPTORW` с `FD_ATTRIBUTES \| FD_FILESIZE \| FD_WRITESTIME \| FD_PROGRESSUI`; обёртка `RemoteFileStream` в COM `IStream` | FR-FCB-6, 8, 9, 10 |
| `OleClipboard` | Windows | P/Invoke `OleSetClipboard`, `OleIsCurrentClipboard`, регистрация форматов | FR-FCB-6 |
| `ClipboardSync` (доработка) | App | Файлы — первым делом при изменении буфера; отправка `FileOffer`; приём и помещение виртуальных файлов в буфер; отзыв при выключении синхронизации и в конце сессии | FR-FCB-1, 5, 18 |
| Плашка / окно просмотра | App | Строка уведомлений: «Передача файлов: имя, 45%», «Не передано: 2,0 ГБ > 500 МБ» | FR-FCB-19, 20 |

### Уточнение FR-FCB-5
«Набор действует, пока на источнике не изменился буфер» реализуется так: набор заменяется, когда источник отправляет
**новое** содержимое буфера (текст, картинку или другой набор), выключает синхронизацию или сессия заканчивается.
Посторонние изменения буфера, которые синхронизация не передаёт, набор не отзывают. Это совпадает с поведением
для пользователя и позволяет проверять функцию двумя экземплярами на одном ПК (у них общий буфер).

## 5. Этапы

Каждый этап — сборка без предупреждений, зелёные тесты, короткий отчёт.

### Этап 1. Протокол v3 и фоновая очередь
- Сообщения из §3, сериализация, `ProtocolVersion = 3`.
- Фоновая очередь в `Connection` (`Send(message, background: true)`).

**Тесты:** сериализация каждого нового сообщения; при заполненной фоновой очереди обычное сообщение уходит раньше следующего фонового.

### Этап 2. Источник
- `FileOfferBuilder`, `FileTransferSource`.

**Тесты (на временной папке):** структура и пустые папки; кириллица; лимиты (размер, количество); `FileOpen` с чужим `offerId` / индексом вне набора / индексом папки → ошибка; файл удалён → `NotFound`; файл изменился → `Changed`; окно 1 МБ не превышается без `FileAck`; `FileCancel` останавливает отправку.

### Этап 3. Получатель: проверка имён и поток
- `FileNameValidator`, `RemoteFileStream`.

**Тесты:** `..\..\Windows\evil.dll`, `C:\x`, `\\server\x`, `CON.txt`, `a:b`, слишком длинные имена — отклоняются; нормальные русские имена — принимаются. Поток: чтение по частям, `FileAck`, таймаут 15 с, закрытие раньше конца → `FileCancel`, `FileError` → исключение.

### Этап 4. Виртуальные файлы Windows (главный риск)
- `VirtualFileDataObject`, `OleClipboard`.
- **Первым делом** — прототип: один файл из памяти в буфер, вставка в Проводник. Проверить, на каком потоке приходят вызовы и что Проводник показывает своё окно прогресса в асинхронном режиме.

**Тесты:** в процессе — запрос `FileGroupDescriptorW` и `FileContents` через `IDataObject.GetData`, разбор дескриптора, чтение потока. Вручную/UI Automation — вставка в Проводник.

### Этап 5. Интеграция и сквозная проверка
- Доработка `ClipboardSync`, уведомления на плашке и в окне просмотра.
- Сквозной автотест по loopback с TLS: набор → чтение каждого файла через получателя → SHA-256 совпадает (файлы до 20 МБ, папки, пустая папка, кириллица).
- Два экземпляра на одном ПК: копирование в Проводнике → вставка в другую папку (UI Automation); отмена посреди большого файла; FPS во время передачи 300 МБ.

### Этап 6. Документы и релиз
- README, отметки о статусе в этом плане, `spec.md` §5.6 (FR-CLP-7 → ссылка на эту спецификацию).
- Проверка с ноутбуком по критериям приёмки 1–9, релиз v0.3.0.

## 6. Риски

| Риск | Последствие | Что делаем |
|---|---|---|
| Вызовы Проводника приходят на UI-поток | Окно просмотра замирает во время вставки | Проверяется прототипом на этапе 4; запасной путь — создавать объект и потоки на отдельном MTA-потоке |
| Проводник не включает асинхронный режим для нашего объекта | Проводник «висит», пока идёт копирование | Прототип на этапе 4; при неудаче — прогресс в своём окне и запись во временную папку (запасной вариант ВФ1) |
| Особенности дескриптора (папки, даты, размеры) | Неверная структура или «0 байт» | Автотест разбора дескриптора; сравнение SHA-256 в сквозном тесте |
| Большая передача забивает канал | Падает FPS, растёт задержка ввода | Фоновая очередь + окно 1 МБ; замер на этапе 5 |
| Антивирус блокирует чтение файла на источнике | Ошибка для этого файла | Код `AccessDenied` → ошибка Windows только для него (FR-FCB-12) |
| Повторная вставка во время идущей передачи | Два параллельных чтения одного файла | Каждый поток — свой `requestId`; ограничение 4 одновременных передачи на набор |

## 7. Ход работ (точка остановки 2026-10-23)

**Порядок изменён:** прототип этапа 4 (главный риск) начат раньше этапов 1–3. Этапы 1–3 ещё не начаты.

### Сделано (не закоммичено)
- `src/RemoteConnect.Windows/Clipboard/VirtualFileDataObject.cs` — COM `IDataObject` + `IDataObjectAsyncCapability`:
  `FileGroupDescriptorW` (дескриптор 592 байта на элемент, флаги ATTRIBUTES|WRITESTIME|FILESIZE|PROGRESSUI|UNICODE),
  `FileContents` → `IStream`, `Preferred DropEffect` = копирование, перечислитель форматов, статический `Trace` для журнала.
- `src/RemoteConnect.Windows/Clipboard/ComStreamAdapter.cs` — COM `IStream` (только последовательное чтение) поверх .NET `Stream`.
- `src/RemoteConnect.Windows/Clipboard/OleClipboard.cs` — `OleSetClipboard` с повторами, `OleInitialize` на потоке, `IsCurrent`, `ClearIfCurrent`.
- `Interop/NativeMethods.cs` — `OleInitialize`, `OleSetClipboard`, `OleIsCurrentClipboard`, `RegisterClipboardFormat`, `GlobalAlloc/Lock/Unlock/Free`.
- Прототип-стенд (вне репозитория): `scratchpad\vfprobe` — кладёт в буфер папку с подпапками, текстовый файл и «медленный» файл 20 МБ.

### Результаты прототипа
1. **Буфер требует `OleInitialize`** на STA-потоке (WinForms его не вызывает, WPF вызывает) — добавлено в `OleClipboard`.
2. **Список файлов работает:** при вставке (`Shell.Application … InvokeVerb("paste")`) Проводник запросил
   `Preferred DropEffect` и `FileGroupDescriptorW` и создал **все папки, включая пустую вложенную**.
3. **Риск подтвердился: вызовы Проводника (из другого процесса) приходят на STA-поток, положивший объект в буфер**,
   а не на потоки RPC. В приложении это был бы UI-поток → блокирующее чтение по сети заморозит окно.
   **Решение (запасной путь из §6):** отдельный STA-поток с циклом сообщений только для буфера с файлами:
   на нём создаётся объект, вызывается `OleSetClipboard`, и на нём же выполняются вызовы Проводника.
4. **Не решено: Проводник не запросил содержимое файлов** (`FileContents` ни разу не вызван, `GetAsyncMode` тоже) —
   файлы не создались, только папки. Проверка настоящим Ctrl+V в окне Проводника была прервана.

### Следующие шаги
1. Разобраться с п. 4. Гипотезы для проверки по очереди:
   - Проводник запрашивает `IDataObjectAsyncCapability` и не получает его (нужно залогировать `QueryInterface` —
     через `ICustomQueryInterface`), из-за чего ведёт себя иначе;
   - для файлов нужен формат `FileContents` в перечислителе с конкретным `lindex` или `TYMED_HGLOBAL` как запасной вариант для маленьких файлов;
   - `InvokeVerb("paste")` из PowerShell отличается от Ctrl+V в Проводнике — проверить настоящим Ctrl+V
     (**предупредить пользователя заранее**: откроется окно Проводника и будет нажато Ctrl+V).
2. Вынести буфер с файлами на отдельный STA-поток (п. 3) и проверить, что окно приложения не замирает.
3. Затем этапы 1–3 (протокол v3, источник, получатель) и далее по плану.

**Важно для проверок:** тесты с Проводником открывают окна и нажимают клавиши на экране пользователя — перед ними нужно коротко предупредить сообщением (подтверждения не ждать).
